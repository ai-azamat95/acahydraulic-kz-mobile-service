## 2. Общий стиль

Сохранить тёмный промышленный характер утверждённых изображений: чёрный/графитовый фон, дымчатая фотографическая фактура, светло-серые буквы, приглушённые золотистые акценты. Никакой белой темы, ослепительно белого основного текста, неонового жёлтого, ярко-зелёной панели WhatsApp или произвольных цветных градиентов.

Начальные ориентиры CSS-токенов: фон #0B0E11, поверхность #1B2023, основной текст #C7C7D1, вторичный #A9ABB4, акцент #C19A48. Уточни их по изображениям. Для насыщенности цифр и иконок ориентируйся на приглушённый первый экран: пользователь специально попросил сделать их тусклее. Цвета должны быть едиными между четырьмя секциями, читаемыми и близкими к эталону.

Шрифт — Inter или максимально близкий уже подключённый обычный sans-serif с качественной кириллицей. Заголовки крупные, плотные, умеренно жирные; пояснения — обычного начертания. Не использовать ультраузкий Bebas для новых заголовков, если он заметно меняет облик относительно эталона. Не заявляй, что точно установлен шрифт из растрового изображения: проверяй сходство форм букв по скриншотам. Размеры, межстрочные интервалы и переносы адаптируй под реальные устройства без обрезания текста.

Кнопки прямоугольные, контурные, с тонкими золотистыми/серыми рамками и стрелкой. Не создавать карточку вокруг каждой строки. Сохранить свободные промежутки и простую иерархию.

Одна общая шапка: исходный геометрический знак, латинские ACA / HYDRAULIC, TikTok, YouTube и меню. Слово SERVICE в бренде не добавлять. Повторяющуюся шапку на четырёх макетах не дублировать четыре раза в DOM.

Одна общая мобильная нижняя панель: «Позвонить» и «WhatsApp», графитовый фон, золотистые контурные значки, серый текст, тонкий разделитель. Учесть safe-area и высоту панели. На desktop контактные действия расположить удобно в шапке/секции, не растягивать мобильную панель на весь широкий экран без необходимости.

Новые стили ограничить областью главной, например .home-v2. Не менять глобально типографику, кнопки, формы и цвета каталога или других страниц.

## 4. Mobile и desktop — обязательные отдельные композиции

Mobile: последовательные четыре секции с ощущением полноэкранных блоков. Высота через min-height, с учётом шапки и нижней панели, возможность роста по содержимому. Допустим CSS scroll-snap-type: y proximity. Не перехватывать каждый touch/wheel и не запирать содержимое height:100vh + overflow:hidden. Все тексты и ссылки доступны в исходном/предварительно отрендеренном HTML без свайпа. Учитывать prefers-reduced-motion и размер текста пользователя.

Desktop: полноценная широкая композиция с контейнером примерно 1200–1440 px. В секциях 1–3 текст/действия слева, визуальный объект справа; статистику первого экрана можно расположить горизонтальной полосой. Для четвёртой секции — крупное видео и сбалансированный соседний блок действий/ссылок. Сохранять цвета, шрифтовой характер и пропорции; не растягивать вертикальный макет на весь монитор. Ограничивать длину строк, использовать разумный clamp() для заголовков. На очень широком экране сохранять композицию и поля.

Контрольные размеры: 360×800, 390×844, 768×1024, 1440×900 и 1920×1080. Обязательны реальные скриншоты всех четырёх секций на 390×844 и 1440×900. Сравни их с референсами и исправь конкретные расхождения до отчёта. Высота секции может превышать viewport для читабельности; не уменьшать шрифт до нечитаемого ради формального одного экрана.

Если доступно, отдельно зафиксировать SHA/ID последнего успешного production-выпуска; не называть main автоматически опубликованной версией без подтверждения.
2. Подготовить общие токены и изолированные компоненты главной. Сохранить совместимость маршрутизации, форм, каталога и измерения. Использовать имеющиеся зависимости; не менять lockfile или платформу без конкретной необходимости.
3. Последовательно реализовать секции 1 → 2 → 3 → 4 и широкие версии. Подключить реальные действия и сохранить footer/формы.
4. Проверить полную сборку, включая scripts/render-static-pages.tsx и scripts/create-spa-route-copies.mjs после pnpm build согласно .github/workflows/pages.yml. Одной vite build недостаточно. Код новых компонентов должен быть SSR-safe: никакого обращения к window/document во время серверного render. Проверить ошибки гидратации и прямое открытие существующих URL.
5. Выполнить релевантные проверки TypeScript, проекта, маршрутов, CTA, формы/калькулятора, consent и существующих SEO/каталоговых ограничений. Учесть, что Mac пользователя имеет 8 ГБ ОЗУ: тяжёлые проверки выполнять последовательно, не запускать параллельные полные сборки. Не ослаблять checks лишь ради зелёного результата. Старые тесты, жёстко завязанные на прежнюю композицию, обновить по утверждённому дизайну с сохранением функциональных инвариантов.
6. Проверить мобильный/компьютерный вид реальным браузером. Скриншоты → визуальное сравнение с четырьмя эталонами → исправление выявленных проблем. Проверить меню, возврат назад, видео, все CTA, длинный текст, открытое модальное окно, клавиатуру и нижнюю панель. Проверить отсутствие горизонтального скролла и перекрытий.
7. Зафиксировать только изменения задачи отдельными осмысленными коммитами. Подготовить docs/homepage-four-screens-verification.md и docs/homepage-four-screens-rollback.md с реальными результатами, ограничениями и конкретными SHA/командами. Не использовать reset --hard, git clean, force-push или действия, уничтожающие чужую работу. Не публиковать секреты и не выводить содержимое auth/config/env с учётными данными.
8. Передать готовую предварительную версию и сведения для отдельного draft PR. Основную ветку не сливать и основной домен не публиковать автоматически. Если удалённая публикация preview недоступна, оставить работающий локальный preview, точную команду, артефакты и честно указать это ограничение; не останавливаться раньше реализации по этой причине.
